# Issue #6: KDE: плотность без заранее выбранной формы

- **State:** Open
- **Created:** 2026-10-12
- **Source:** https://github.com/kshakirov/Agnostic-Inference-Engine/issues/6

## Зачем

Четыре параметрические версии форму latency не вытянули. Вместо коллекционирования новых распределений иду к KDE: строю плотность прямо из данных, но без magic `.fit()`.

## Что уже пощупал

На ручной выборке `[1, 2, 2, 3, 7]` собрал Gaussian-ядро, вклад отдельной точки и полную оценку

```text
f(x) = сумма ядер / (n h)
```

Проверил симметрию: равноудалённые точки дают одинаковый вклад. Для `x=2`, `h=1` получилось `0.256365`. Затем сделал первый leave-one-out шаг: удалил `x=1` и оценил плотность в этой же точке по оставшимся данным — `0.134483`.

## Следующий ход

1. Пройти leave-one-out по всей ручной выборке.
2. Понять и собрать критерий выбора ширины `h`.
3. Только после этого применить прибор к реальным latency B/C.

Python пока Ground Truth. После понимания механику вынесу в чистый модуль.

## Comment: leave-one-out добит на ручной выборке

Источник: https://github.com/kshakirov/Agnostic-Inference-Engine/issues/6#issuecomment-6138532331

Leave-one-out добил на ручной выборке.

Для каждого наблюдения теперь:

```text
убираю x_i
-> строю KDE по оставшимся n-1 точкам
-> оцениваю плотность в удалённой x_i
-> беру log
-> усредняю
```

На пробной сетке ширин получилось:

```text
h=1  score=-3.4635
h=2  score=-2.5180
h=3  score=-2.5027  <- пока лучший
h=7  score=-2.9718
```

Механика cross-validation работает: слишком узкое и слишком широкое ядро проигрывают.

Следующий ход: заменить стартовый `-100` на `-∞`, возвращать не только лучший score, но и сам `h`, затем сделать отдельную осмысленную сетку ширин. Перебирать значения самой выборки как `h` — только ручной стенд, не финальный алгоритм.

## Comment: bandwidth нашёл, но KDE case ещё не закрываю

Источник: https://github.com/kshakirov/Agnostic-Inference-Engine/issues/6#issuecomment-6333077797

На 600 реальных POST-latency перевёл leave-one-out KDE с тройного Python-цикла
на батчевую матрицу попарных разностей.

Правило Сильвермана дало стартовый ориентир:

```text
h_silverman = 0.0604828 ms
```

От него прошёл геометрической сеткой, окружил максимум и разбил найденный
интервал на десять частей:

```text
h = 0.00855356 ms
LOO mean log-score = 0.4706943
```

Важная поправка: итоговую плотность сначала по инерции посчитал со
`h_silverman`. Это обнуляло смысл всего LOO-поиска. Исправил: финальная KDE
использует выбранный `h`.

Bandwidth case для этой выборки считаю закрытым. Весь KDE case пока не закрываю:

- это только первые 600 наблюдений одного POST-прогона;
- плотность пока вычисляется в наблюдаемых точках, а не на отдельной сетке `x`;
- расчёт ещё живёт в экспериментальном скрипте, а не в `inference_core`;
- прибор надо проверить на другой независимой выборке.

## Comment: kernel regression упёрлась в смену режима

Источник: https://github.com/kshakirov/Agnostic-Inference-Engine/issues/6#issuecomment-6461654230

Перешёл от KDE к kernel regression на живых POST-данных.

Взял `run-001`: 13 размеров тела, по 1000 latency на каждый. Размеры перевёл
в `log2`, чтобы каждое удвоение имело одинаковое расстояние. Для выбора `h`
сделал leave-one-size-out: обнуляю весь блок наблюдений проверяемого размера,
перенормирую веса и сравниваю прогноз с его эмпирическим средним.

На первой сетке:

```text
h = 0.25 -> MSE = 303139.67  <- минимум на границе
h = 0.50 -> MSE = 303746.16
h = 0.75 -> MSE = 319786.23
h = 1.00 -> MSE = 355170.25
```

Это не победа `h=0.25`. Последние две точки живут уже в другом режиме: на
`32768` и `65536 B` сервер насыщается, latency скачет на порядки и забивает
общую ошибку. Одна гладкая регрессия всю линию не описывает.

Следующий ход: отдельно выбрать bandwidth на рабочем участке `16..16384 B`,
а `32768..65536 B` оставить не «выбросами», а зафиксированным переходом в
насыщение.
