# PLAN-LATENCY-001 — От сервера к модели

Живой план реального эксперимента. Нужен, чтобы в любой момент открыть страницу и вспомнить: где находимся, зачем делается текущий шаг и что будет следующим.

## Цель

Не подобрать красивую формулу к старым latency, а построить модель, которая при явно заданном режиме сервера:

- сжимает наблюдения в понятные параметры;
- честно показывает неопределённость этих параметров;
- предсказывает новые данные;
- имеет заранее понятные условия поражения.

```text
объект != данные != модель != оценки параметров
```

## Общий маршрут

```text
зафиксировать режим эксперимента
-> сохранить сырые наблюдения
-> проверить устойчивость режима
-> описать данные без параметрической модели
-> выставить конкурирующие модели
-> оценить параметры и их неопределённость
-> проверить прогноз на новых данных
-> оставить рабочую модель или зафиксировать её поражение
```

## Раунд 1 — Один режим или несколько

Практический вопрос:

> Можно ли latency при фиксированной нагрузке считать одной устойчивой выборкой из одного распределения?

Две версии:

```text
H1: режим достаточно устойчив, наблюдения можно объединить.
H2: режим меняется, а одна модель склеивает разные состояния сервера.
```

Протокол фиксирует:

- сервер и endpoint;
- вид запроса;
- конкуррентность или интенсивность;
- прогрев;
- длительность измерения;
- время и latency каждого запроса.

Последовательность делится на временные блоки. Между блоками сравниваются среднее, разброс, квантили и эмпирические распределения.

`H1` проигрывает, если блоки систематически различаются сильнее обычного выборочного разброса. В этом случае спор о Normal против Lognormal пока преждевременен: сначала надо описать изменение режима.

## Следующие раунды

### Раунд 2 — Данные без выдуманной формы

Построить ECDF, основные квантили, моменты и посмотреть хвосты. Это описание полученной выборки, а не утверждение об истинном распределении сервера.

### Раунд 3 — Конкурирующие модели

Предложить минимум две различимые версии. Normal не назначается победителем заранее. Для каждой версии выписать предположения и наблюдаемый признак, способный её опровергнуть.

### Раунд 4 — Оценки и неопределённость

Получить MLE параметров. Затем оценить не только сами параметры, но и их разброс: через Фишера, стандартные ошибки, интервалы, bootstrap или точную теорию — смотря что допускает модель.

### Раунд 5 — Новые данные

Не использовать проверочную серию для подгонки. Сравнить предсказанные распределение, квантили и интервалы с новой временной серией.

### Раунд 6 — Решение

Оставить модель только с указанием режима применимости и обнаруженных слабых мест. Если ни одна версия не выдержала проверку, это нормальный результат: фиксируется, какой информации или какой структуры не хватило.

## Контракт модели

Для каждой модели должны быть записаны:

- предположения;
- оцениваемые параметры;
- способ получения оценок;
- оценка их неопределённости;
- критерии соответствия данным;
- проверка прогноза;
- конкурирующие версии;
- условия поражения.

Коротко:

```text
модель = предположения + оценки + неопределённость + проверка + условия поражения
```

## Текущая точка

Синтетический Gaussian-стенд уже проверяет механику MLE и Фишера там, где Ground Truth известен.

Реальный стенд поднят:

```text
GET http://127.0.0.1:9000/
нагрузка: 10 req/s
прогрев: 10 s
измерение: 60 s
наблюдений: 600
ошибок HTTP: 0
```

Vegeta сохраняет timestamp и latency в наносекундах. Исходные `.gob` и `.csv` лежат в `experiments/latency/2026-08-31-baseline-a/`.

Выяснилась неприятная, но полезная вещь: старые средства не готовы принять этот источник напрямую. Они завязаны на прежний двухполевой кортеж, а `calculate_empirical_moments` вообще считает Bernoulli-статистику статуса, не моменты latency. Название оказалось шире реального контракта.

Поэтому сейчас без архитектурного ремонта делается ad hoc-проход:

```text
CSV Vegeta
-> третья колонка latency_ns
-> перевод в latency_ms
-> эмпирические mean, variance и std с ddof=0
```

Промежуточный результат для 600 latency:

```text
mean     = 0.7333737967 ms
variance = 0.2483922664 ms^2
std      = 0.4983896732 ms
```

Среднее совпало со сводкой Vegeta `0.733 ms`, поэтому колонка и перевод единиц выбраны правильно.

### С чего начать завтра

1. Восстановить физический смысл полученных mean, variance и std и проверить, чего они не говорят о выборке.
2. Решить, какие ещё эмпирические характеристики действительно нужны до параметрической гипотезы. Не добавлять их автоматически.
3. Только после этого решить, какую часть старых статистических средств можно переиспользовать, а что было ложной универсальностью.
4. Затем вернуться к основной цепочке: эмпирика -> гипотеза Normal -> MLE -> неопределённость через Фишера -> проверка гипотезы.
